# 웹 추천 연동 계획

웹 코드(`web/`)와 데이터를 실제로 열어 확인한 뒤 다시 쓴 계획이에요. 아직 만든 파일은 없어요.

## 1. 지금 웹은 이렇게 되어 있어요

| 항목 | 현재 상태 |
| --- | --- |
| 구조 | `index.html` 하나 + `js/app.js`(1,497줄, 프레임워크 없음) + `css/style.css`. 화면(`page/*.html` 5개), 헤더, 사이드바를 `app.js`가 불러와 `#Main` 같은 주소(해시)로 전환해요. |
| 곡 데이터 | `data/catalog.json`: `tracks` 350곡(Jamendo 곡 정보와 음원 주소)과 `songMap` 355쌍(`[KKBox song_id, Jamendo id]`, KKBox 곡은 344개). `tools/build_catalog.py`가 Jamendo 수집 CSV에서 만들어요. |
| 홈 추천 | 지금은 `listens`(Jamendo 재생 수) 순 인기곡이에요. 모델 추천은 연결되어 있지 않아요. |
| **모델 연결 지점(이미 있음)** | `app.js` 맨 아래 `MusicApp.setModelRecommendations([KKBox song_id, ...])`. 추천 순서의 KKBox ID를 넘기면 Jamendo 곡으로 바꿔 홈 `rail-Main` 목록에 보여 줘요. 연결된 곡이 하나도 없으면 인기곡을 그대로 둬요. |
| 사용자 | 웹에는 사용자 개념이 없어요. 프로필(닉네임·장르 3개)은 브라우저 `localStorage`에만 저장돼요. |
| 재생 | 곡을 누르면 Jamendo 음원이 재생돼요(`<audio>`). |

→ 웹은 **"KKBox 곡 ID 목록 한 개"만 받으면** 추천을 그릴 수 있어요. 서버가 할 일은 그 목록을 만들어 주는 것이에요.

## 2. 쓸 데이터

| 데이터 | 위치 | 쓰는 곳 | 확인한 내용 |
| --- | --- | --- | --- |
| 웹 곡 목록 | `web/data/catalog.json`의 `songMap` | 추천 후보 = KKBox 곡 **344개** | 344곡 모두 Jamendo 곡 정보가 있어요. |
| 곡 메타데이터 | `music data/song_data.csv` | 곡 길이, 장르, 아티스트, 언어 | 344곡 모두 행이 있고, 장르 코드는 334곡에 있어요. |
| 청취 기록 | `data.csv`(7,352,114행, 사용자 30,751명) | 사용자·아티스트·장르 이력으로 특성 만들기 | 웹 곡 344개 중 **42곡만** 기록이 있고 각각 1~2번뿐이에요. |
| 모델 | `ML 개발/v11/` (`modelA_v11_models.joblib`, `.cbm`) | 점수 계산 | 수정하지 않아요. |
| 특성 코드 | `전달용_코드패키지/A/v11.py` | 특성 129개 계산 | v6 특성이 이 파일 안에 있어서 이것만 있으면 돼요. 특성 생성은 약 70초예요. |
| 보정 설정 | `전달용_코드패키지/B/b2_policies.py`, `results/policies.json` | `p − λ × 인기도 백분위` | λ=0.20(한도 1%p 설정). 인기도 백분위 기준은 검증 구간의 `s_cnt_now` 분포예요. |

**데이터에서 중요한 사실 두 가지**

1. **웹 곡 302곡은 청취 기록이 없어요.** 곡 이력 특성(곡 재생 횟수, 곡 재청취율 등)은 0이고, 곡 길이·장르·아티스트·언어(`song_data.csv`)와 사용자 이력 특성만 채울 수 있어요. 웹 곡의 아티스트 128명 중 20명, 장르 30개 모두는 `data.csv`에도 있어서 "사용자가 이 아티스트·장르를 들어 왔는지" 특성은 계산돼요.
2. **특성은 시간 순서대로 누적**돼요(그 행 이전 기록으로 계산). 그래서 데모 쌍은 `data.csv` 맨 뒤에 새 행으로 붙여서 계산해요. 쌍 행끼리 서로의 횟수에 섞이지 않게 처리가 필요해요.

## 3. 어떻게 할지

### 3.1 흐름

```
[오프라인, 한 번]                         [서버, 요청마다]                     [웹]
데모 사용자 3~4명 선정                    사용자 선택 요청 받음                 사용자 카드 선택
 → 사용자×웹곡 344쌍씩 만들기              → 저장된 특성으로 v11 모델 실행       → 서버에 요청
 → v11.py 코드로 특성 129개 계산            → 기존 추천 상위 10곡                → KKBox ID 목록 받음
 → 파일로 저장                              → 보정 추천 상위 10곡                → MusicApp.setModelRecommendations
                                            → KKBox ID 순서만 반환                  로 홈에 표시
```

### 3.2 쌍 만들기 규칙

| 항목 | 값 |
| --- | --- |
| 사용자 | 데모 3~4명. 청취 기록이 충분하고 취향이 서로 다른 사용자를 `data.csv`에서 고름. 화면에는 "데모 사용자 A~D"만 표시 |
| 곡 | 웹 곡 344개 전부 |
| 재생 경로 | `discover` 탭으로 고정: 화면 `Online playlist more`, 타입 `online-playlist` (`discover` 탭 행 중 가장 흔한 조합) |
| 곡 정보 | `song_data.csv`에서 채움 |
| 정답(`target`) | 모르므로 0으로 두고, 지연 재청취율 계열에 들어가지 않는지 확인 |

### 3.3 서버가 하는 일

1. `joblib`의 `features`(129개) 순서로 열을 맞춰 4개 모델(LightGBM, LightGBM_B, CatBoost, XGBoost)에 넣고 스태킹으로 점수 `p`를 계산해요. CatBoost는 `.cbm`을 따로 불러와요.
2. `p` 순 상위 10곡 = **기존 추천**.
3. `p − 0.20 × 인기도 백분위` 순 상위 10곡 = **보정 추천**. 백분위 = `searchsorted(REF, log1p(s_cnt_now)) / len(REF)`.
4. KKBox `song_id` 순서만 돌려줘요. 점수, λ, 모델 이름은 보내지 않아요(기능정의서 D4).

### 3.4 웹에서 바꿀 곳

| 파일 | 변경 |
| --- | --- |
| `js/app.js` | 서버 주소 한 줄, 데모 사용자 선택 시 서버 요청, 응답을 `MusicApp.setModelRecommendations`에 전달. 기존·보정 두 목록을 보여 주는 부분 추가 |

안내 문구: "같은 모델을 다른 곡에 적용한 시연이에요. 홈 추천을 KKBox의 `discover` 탭 재생으로 간주했고, 정확도 검증이 아니에요. 곡 연결은 동일 녹음으로 확정되지 않았어요."

### 3.7 곡 이력 특성이 0인 곡(302곡) 처리

| 방법 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| **A. 0 그대로 (권장)** | 곡 횟수·곡 재청취율 등 곡 이력 특성을 0(또는 결측)으로 둠 | 모델·입력 방식 수정 없음. 학습 데이터에도 "곡이 처음 재생되는 시점"은 이력 0으로 들어 있어서(누적 횟수가 0에서 시작) 모델이 본 적 있는 상태 | 302곡은 점수가 사용자·아티스트·장르 특성으로만 갈려 서로 비슷할 수 있음 |
| B. 이력 있는 42곡만 사용 | 후보를 42곡으로 줄임 | 곡 특성이 실제 값 | 후보가 적어 추천 10곡이 웹 곡 전체를 대표하지 못함 |
| C. 아티스트·장르 평균으로 대체 | 같은 아티스트·장르 KKBox 곡의 이력을 곡 특성에 대신 넣음 | 점수 차이가 커짐 | 모델이 학습 때 못 본 입력이라 의미를 검증할 수 없음. "모델을 그대로 쓴다"는 설명과 어긋남 → 쓰지 않음 |

**진행 방식**: A로 먼저 돌리고, 5단계 점검에서 사용자 A~D의 상위 10곡이 서로 얼마나 다른지 본다.
- 충분히 다르면 A 그대로 간다.
- 너무 비슷하면 (1) 취향이 더 다른 사용자로 교체하고, (2) 그래도 같으면 B로 줄이거나 현재 결과를 그대로 보여 주고 한계로 명시한다. C는 쓰지 않는다.

## 5. 남은 위험

1. **사용자 간 차이가 작을 수 있어요.** 302곡은 곡 이력이 0이라 점수가 사용자 쪽 특성과 아티스트·장르로만 갈려요. 5단계에서 사용자별 상위 10곡이 충분히 다른지 먼저 봐요. 대응 방법은 3.7절에 정리했어요.
2. **쌍 행을 누적에서 제외하는 구현**이 `v11.py`와 같은 값을 내는지는 4단계 이전(2단계)의 대조로만 확인돼요.
3. **곡 연결이 확정이 아니에요.** KKBox 곡과 Jamendo 곡은 같은 녹음이 아닐 수 있어요(안내 문구에 명시).
4. **서버 배포**: Vercel 정적 사이트로는 안 되고, 지금은 이 컴퓨터에서 로컬 시연만 해요.

## 7. 변경: 장르별 데모 사용자 11명 + 회원가입 장르 연동 (2026-11-05)

기존 데모 사용자 A~D는 지우고, `genres.json`의 장르 11개마다 그 장르를 가장 많이 듣는 실제 KKBox 사용자 1명(서로 다른 사람)으로 바꿨어요. 6장의 A~D 관련 숫자는 이 변경 전 결과예요.

**동작**
1. 회원가입에서 고른 장르(최대 3개)를 프로필에 저장해요.
2. 홈을 열면 서버에 `GET /api/recommend?genres=힙합,재즈,록·메탈`을 요청해요. 서버는 장르별 사용자의 v11 점수 순서를 한 곡씩 번갈아 섞어 10곡을 돌려줘요.
3. 처음엔 기존 추천만 보여 줘요(기존/보정 두 목록 표시는 없앴어요).
4. 서로 다른 3곡을 들으면 미리 계산해 둔 보정 추천으로 바꾸고 알림을 띄워요. 들은 곡으로 서버가 다시 계산하는 건 아니에요.
5. 서버가 없거나 장르를 모르면 인기곡을 보여 줘요.

**사용자 선정** (`prepare_pairs.py`): 웹 곡을 장르 11개로 나누고, 장르마다 웹 곡이 가진 KKBox 장르 코드 상위 3개의 재생 비중이 가장 높은 사용자(청취 400회 이상)를 구분이 쉬운 장르부터 겹치지 않게 선정. 대표 코드 비중: 팝 0.51, 록·메탈 0.26, 일렉트로닉 0.34, 영상 음악 0.56, 힙합 0.26, 월드 0.17, lofi 0.28, 포크 0.80, 재즈 0.31, R&B 0.59, 기타 0.41.

**검증**: 새 쌍 3000번, 777번을 원본 `v11.py` 특성 코드(쌍 1개)와 대조해 특성 129개 일치 여부를 확인(3000번 일치). 장르 11명의 상위 10곡 겹침은 55쌍 중 33쌍이 0곡, 평균 1.56곡, 7곡 이상 겹치는 쌍은 팝–포크, 일렉트로닉–lofi, R&B–포크, R&B–기타, 포크–기타.

**한계**: 장르 코드가 거칠어서 사용자의 실제 취향이 장르 이름과 어긋나요(예: "재즈" 사용자는 힙합 아티스트, "R&B"·"팝"·"포크" 사용자는 중화권 가요를 주로 들음). 보정은 장르 11명 중 7명에서만 순서를 바꾸고(팝, R&B, 월드, 영상 음악, 기타는 기존과 같음) 곡 집합은 거의 같아요.
